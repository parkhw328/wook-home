# 프로젝트 운영 및 개발 원칙

이 문서는 현재까지의 대화를 정리한 설계 기준이다. 구현 완료를 의미하지 않는다. 기능과 검증 기준은 [requirements.md](requirements.md)를 함께 참고한다. 추가 결정은 사용자가 이어서 작성한다.

## 1. 제품 방향 — 합의

- 여러 AI 에이전트를 직원으로 표현하는 가상 회사 GUI를 만든다.
- 사용자는 Commander로서 업무를 지시하고, 질문에 답하며, 결과를 판단한다.
- 초기 공급자 대상은 OpenAI, Claude, Meta의 Muse, Google Gemini다. 실제 연결 제품·CLI·API는 별도로 확정한다.
- 공간과 캐릭터에 실제 업무 상태를 연결한다. 시각적 구성은 대화에서 합의한 내용을 기준으로 구체화한다.
- 개발 전에 rules와 requirements를 정리하고, 이를 기준으로 범위를 구체화한다.
- 사용자 편의를 기능 구현의 우선 기준으로 삼는다. 기본 사용 흐름에서 CLI 옵션·설정 파일·문서의 위치를 사용자가 알아내도록 요구하지 않고, 목적별 설정과 현재 상태·다음 행동을 화면에서 제공한다.

## 2. 실행 및 배포 — 합의

- 각 작업 PC에서 Docker 기반 환경을 실행하고 로컬 웹 GUI로 접근한다.
- 사용자가 다른 PC에서 확인하도록 요청하면 Docker 바인딩 주소와 서버 접속 주소를 명시적으로 설정해 네트워크 접속을 허용한다. 기본값은 로컬 접속이며, 인증·클라우드 운영과 브라우저 확장의 원격 연결은 별도 범위다.
- Docker Compose를 기본 구성안으로 삼는다. Electron 설치형은 초기 필수 범위가 아니다.
- PC를 이동할 때 기존 PC의 작업을 중지하고 GitHub를 통해 코드와 인계 내용을 전달한다.
- 초기에는 여러 PC가 같은 업무를 동시에 계속 수행하는 방식이나 실행 프로세스의 실시간 이동을 목표로 하지 않는다.
- 로컬 임시 에이전트는 단순 업무 중심으로 사용한다.
- 계속 실행해야 하는 업무는 향후 클라우드에서 컨테이너를 상시 운영하는 형태로 확장한다.

## 3. 직원과 세션 — 설계 원칙

- 직원의 정체성(이름·역할·설정)과 실행 세션을 분리한다.
- 직원·연결 관리는 CLI와 웹 감지를 함께 제공한다. 감지 대상에서 새 직원을 등록하거나 같은 공급자의 기존 직원에 연결하고, 직원 상세에서 연결 종류·현재 상태·가능한 작업을 확인한다. 같은 감지 항목의 중복 등록을 막고 연결 변경·해제를 지원한다.
- 직원 등록이 실행·로그인·메시지 전송 권한을 추가하지 않는다. 웹 탭과 연결이 확인되지 않은 CLI 프로세스는 관찰 전용이며 지원되는 Codex 대화만 기존 지시 경로를 사용한다. 탭 닫힘·프로세스 종료·감지 연결 끊김에도 직원 정보는 유지한다.
- 직원 이름·역할·공급자와 사용자가 선택한 연결 종류만 로컬 DB에 보관한다. 관찰 식별자·탭 수·브라우저 별칭·프로세스 정보와 연결 매핑은 메모리에만 두고 인계에서 제외한다. 서버 재시작 후 직원은 다시 연결 필요로 표시하며 현재 목록에서 명시적으로 재연결한다.
- 신규 직원 실행과 기존 세션 연결을 모두 목표로 하되, 공급자별 지원 범위를 구분한다.
- 세션 관찰, 저장된 세션 재개, 실행 중 세션의 실시간 제어를 같은 기능으로 취급하지 않는다.
- Docker 밖의 로컬 세션은 별도 연결 프로그램이나 공식 인터페이스가 필요할 수 있다.
- 같은 계정 로그인만으로 모든 앱의 기존 대화와 실행 상태에 접근할 수 있다고 가정하지 않는다.
- 모델과 추론 강도는 실제 지원 옵션만 노출하고, 변경 적용 시점을 표시한다. 연결한 Codex 직원 상세에서 선택과 지시를 함께 제공하며, 다음 실행의 기본 설정 변경과 지시 큐 접수는 별도로 확인한다. 실행 중인 턴·기존 승인 정책·권한은 이 선택으로 변경하지 않는다.
- 지원되는 CLI의 추가·종료를 실제 프로세스 관찰로 감지한다. 첫 대화 전의 빈 CLI도 표시하며 PID와 시작 시각으로 실행 인스턴스를 구분한다. 대화 기록의 오래된 활동이나 턴 완료를 CLI 종료로 판정하지 않는다.
- CLI 프로세스 감지는 같은 PC의 Windows 로그인 세션 또는 Linux 연결 프로그램과 같은 사용자(유효 UID) 범위임을 표시한다. Linux에서도 Docker 실행과 CLI·웹 감지를 지원하며 호스트 감지기를 CLI와 같은 환경에서 실행한다. 프로젝트별 저장 대화와 분리하고, 근거 없이 프로세스를 대화 UUID에 연결하거나 제어 가능 상태로 표시하지 않는다. 감지 실패·권한 부족·연결 끊김은 종료와 구분하며 최근 종료 기록은 제한된 시간만 유지한다.
- 지원되는 로컬 CLI와 브라우저의 AI 웹 탭을 함께 감지한다. 초기 범위는 기존 Codex CLI 관찰과 Chrome의 ChatGPT·Claude·Meta AI·Gemini 탭이며, 같은 공급자의 여러 세션과 여러 창도 구분한다.
- CLI 기록 관찰, 웹 탭 열림, 식별 가능한 웹 대화, 실제 실행·제어 가능 상태를 구분한다. 새 대화 화면이나 로그인 화면을 실행 중인 에이전트로 표시하지 않는다. 감지 대상이 사라진 경우와 감지 연결이 끊긴 경우도 구분한다.
- 웹 감지는 사용자가 설치·연결한 브라우저 확장프로그램의 해당 프로필로 한정한다. 허용한 AI 사이트의 탭만 확인하며 제목·본문·쿠키·인증 정보·전체 방문 기록을 수집하지 않는다. 웹 탭은 로컬 프로젝트 소속으로 추정하지 않는다.
- 웹 감지 정보는 로컬 메모리에서만 유지하고 Git·Docker 이미지·공개 Wiki·업무 인계에 포함하지 않는다. 같은 대화의 중복 탭은 대화 하나와 탭 수로 표현하며 CLI와 웹의 동일 계정을 동일 세션으로 합치지 않는다.
- 접속 대상은 사무실 서버, 호스트 연결 프로그램, 지원 CLI, 연결한 브라우저, OpenAI·Claude·Gemini·Meta API로 나누어 함께 점검한다. 설치·설정 여부, 감지, 인증 확인, 실제 제어 가능 여부를 각각 표시하고 미지원 대상도 이유와 다음 조치를 안내한다.
- API 점검은 서버에 설정된 인증 정보로 공식 모델 목록을 읽는 범위로 제한한다. 생성·업무 실행을 자동 요청하지 않으며 웹 로그인이나 CLI 구독을 API 인증으로 추정하지 않는다. 확인 시각·시간 초과·인증 거절·요청 제한·응답 오류를 구분하고 오래된 결과는 재점검이 필요하다고 표시한다.
- 비밀 값과 공급자 오류 원문을 화면·로그·점검 응답에 노출하지 않는다. 임의 URL·인증 값을 웹 요청으로 받지 않고 점검 주소를 공식 HTTPS 대상으로 제한한다. 중복 점검은 합치고 재시도 간격과 응답 크기를 제한한다.

- 자료 검색은 기본 감지와 별도로 명시적으로 활성화한다. 선택한 프로젝트의 CLI 공개 메시지와 사용자가 개별 보관을 켠 웹 대화만 로컬 검색 사본으로 저장한다. 웹은 화면에 불러온 공개 메시지와 정규화한 대화 주소로 한정하며 시스템·추론·도구 원문·쿠키·인증 정보는 수집하지 않는다. 알려진 비밀 정보와 개인 경로는 마스킹한다.
- 검색 사본은 CLI 종료·탭 닫힘·서버 재시작 뒤에도 보관하고 업무 DB·인계·Git·이미지·Wiki와 분리한다. 수집을 꺼도 기존 사본은 유지한다. 웹 대화를 로컬 프로젝트로 추정하지 않으며 보관 기록을 실제 실행 종료로 표시하지 않는다. 화면에서 읽지 못한 대화는 명시적으로 알리고 전체 본문 수집으로 대체하지 않는다.

## 4. 데이터와 인계 — 설계 원칙

| 위치 | 저장 대상 |
| --- | --- |
| GitHub | 코드, 공통 설정 예시, 공유 가능한 직원 역할 정의와 업무 인계 기록 |
| 영속 볼륨 | 내부 DB, 로컬 실행 기록, 공급자 세션 데이터, 작업 중간 상태 |
| 별도 인증 설정 | API 키, 로그인 토큰 등 비밀 정보 |

- Docker 이미지와 GitHub에 인증 정보를 포함하지 않는다.
- 개인정보, 비밀번호, API 키, 로그인 토큰 등 중요 정보는 커밋·푸시하거나 로그에 남기지 않는다. 오류 메시지와 실행 출력에도 원문을 노출하지 않고 필요한 경우 마스킹한다.
- Docker 볼륨은 PC 간 자동 공유되지 않는다. GitHub 동기화가 볼륨이나 프로세스 이동을 대신하지 않는다.
- 원본 대화와 내부 기록 전체를 자동으로 GitHub에 올리지 않는다. 공유 범위와 민감 정보 제외 정책은 추가 정의한다.
- 인계 기록에는 목표, 완료 내용, 남은 작업, 관련 파일·커밋, 다음 행동을 남긴다.
- 공급자 세션을 재개할 수 없으면 인계 기록을 바탕으로 새 세션을 시작하며, 원래 세션의 완전 복원으로 표시하지 않는다.
- 정상 종료는 새 업무 접수 중단, 진행 업무 정리 또는 중단, 상태 저장, 종료 순서로 설계한다.
- 클라우드 상시 운영도 재시작과 장애 복구를 고려한다.

## 5. Commander와 화면 — 설계 원칙

- 화면의 작업 상태와 캐릭터 동작은 실제 이벤트에 근거한다.
- 연결 끊김, 실패, 중단, 승인 대기를 작업 완료로 표시하지 않는다.
- 지원되지 않는 제어 기능은 비활성화하고 이유를 표시한다.
- 버튼은 실행·저장·승인, 보조 이동, 주의·취소의 역할별 색상과 굵기를 공통으로 적용한다. 선택 상태는 선과 굵기를 함께 사용하고, 키보드 초점·비활성 상태를 구분한다. 최소 44px 높이와 16px 글씨를 유지하며 새 화면도 requirements.md의 4.4 버튼 기준을 따른다.
- 기존 터미널과 GUI가 같은 세션에 충돌하는 지시를 보내지 않도록 제어권을 관리한다.
- Commander의 승인 대상, 자율 실행 범위, 비용·시간 한도는 별도 정책으로 확정한다.
- 한글은 Noto Sans KR(본고딕 계열), 영문·숫자는 JetBrains Mono를 기본으로 사용한다. 폰트를 자체 제공하고 모든 텍스트 레이블에 축소·원근 변환을 적용하지 않아 가독성을 유지한다.
- 영문·숫자를 장식이라는 이유로 작게 표시하지 않는다. 기본 브라우저 글꼴 16px 기준으로 보조 레이블·상태·시각·버전은 최소 14px, 안내 본문은 15px, 버튼·입력·목록 이름은 16px, 일반 본문·대화는 17px로 표시한다. 같은 역할의 한글·영문에는 같은 크기 기준을 적용하며 상세 기준은 requirements.md의 글자 가독성 절을 따른다.
- 글자 크기는 공통 토큰과 rem 단위로 관리하고 루트 글꼴 크기는 100%로 두어 브라우저 설정을 존중한다. 모바일이나 새 화면에서도 최소 크기를 낮추지 않는다. 공간이 부족하면 줄바꿈·여백·열 배치를 조정하고 글자를 축소하지 않는다. 영문 대문자 소제목의 자간은 0.06em 이하로 제한한다.
- 화면·스타일을 추가하거나 변경할 때 실제 브라우저의 최종 계산 글꼴 크기와 잘림·겹침을 확인한다. CSS 선언만 보고 완료로 판단하지 않으며 사이드바·영문 소제목·입력창·대화창·감지 목록·하단 정보와 320px 모바일까지 점검한다.
- 홈·업무 보드·자료 검색·작업 인계·직원과 연결 관리·모든 대화상자·전체화면에 사용자가 선택한 라이트·다크 테마를 공통 적용한다. 첫 방문은 기기 설정을 따르고 직접 선택한 값은 현재 브라우저에 보관해 화면 이동·새로고침 후에도 유지한다. 기기 설정 자동 반영은 해당 선택일 때만 수행하며 테마 전환이 방·세션·검색·작성·스크롤을 초기화하지 않는다.
- 메인 사무실은 선택한 테마에 맞는 배경·조명과 목재 바닥·청색 유리창·따뜻한 실내 분위기로 구성하고 주요 작업에는 레드 계열 강조색을 유지한다. 다크 테마는 어두운 네이비 배경을 사용한다. 얕고 긴 층을 반복하는 형태 대신 충분한 실내 깊이와 여러 구획을 가진 사무실을 보여 준다. 장식 움직임과 실제 작업 상태를 구분하고 동작 줄이기 설정을 지원한다.
- 사무실 이름은 실행 설정으로 받으며 현재 기본값은 StackQueue Office다.
- 현재 사용자·역할과 로컬 서버 연결 상태를 왼쪽 탐색 영역 최상단에 함께 표시한다. 같은 카드 안에서 사용자·상태 다음에 사무실 이름·로고를 배치한다. 본문 위에 같은 사무실 이름·연결 상태·LOCAL 바를 반복하지 않고, 별도 워크스페이스 카드와 중복 소개 문구도 두지 않는다. 모바일에서도 사용자와 연결 상태를 함께 유지하며 도움말·버전은 하단에 둔다.
- 프로그램·블로그 배너와 버전·사용법 링크는 왼쪽 탐색 영역에 모아 본문 하단을 비운다. 짧은 설명·실제 아이콘·링크를 유지하고 필요하면 접어 둘 수 있게 한다. 작은 화면의 첫 진입은 접힌 상태로 시작하며 자동 갱신 중 펼침 상태와 링크 초점을 보존한다. 연결 상태 문구는 최상단 카드의 전체 폭을 기준으로 가운데 정렬한다.
- StackQueue 네이버 블로그를 소개하는 배너를 프로그램 배너와 함께 제공한다.
- wShell·wPost·wText 소개에는 각 프로젝트의 실제 앱 아이콘을 사용한다. 임의 글자 기호나 유사 로고로 대체하지 않고 색·비율·투명 여백을 유지한다. 자산은 자체 제공하며 원본 출처·버전·라이선스를 함께 보관한다.
- 사용자 메인화면은 실제 사무실처럼 벽·문·복도로 연결된 공간을 중심으로 구성한다. 사무실, 회의실, 대표이사실, 휴게실, 다과실을 각각 독립된 방으로 구분한다. 배경 그림 위의 이름표나 책상 배열만으로 공간 요구사항을 충족한 것으로 보지 않는다.
- 사무실은 여러 층의 높이와 깊이가 보이는 입체 단면 구조로 표현한다. 층마다 독립된 공간이 이어지고, 가구·유리벽·출입구·복도의 높이와 앞뒤 관계를 알아볼 수 있어야 한다. 위에서 내려다보는 2D 평면도를 완료된 형태로 보지 않는다.
- 전체 층 배치와 선택한 층의 내부를 확인할 수 있게 한다. 층 선택 시 해당 층을 독립적으로 펼쳐 책상 사이 통로·유리로 나뉜 방·엘리베이터의 깊이가 보이는 사선 시점으로 보여 준다. Commander와 직원 캐릭터는 책상 사이 통로·복도·출입문·층간 연결 동선을 따라 움직이며, 실제 업무 상태와 공간 표현을 위한 보행 동작을 구분한다. 실제 연결되지 않은 직원을 활동 중인 사람처럼 만들지 않는다.
- 입체 사무실은 가로로 이어지는 방과 긴 복도가 잘 보이도록 배치하고 넓은 화면의 가로 폭을 활용한다. 이동 경로를 구분할 수 있는 안내와 확대·화면 맞춤·전체화면 조작을 제공하며, 전체화면 전환에도 방·선택·대화 초안을 유지한다. 글자 크기를 줄여 공간을 확보하지 않는다.
- 기본 화면은 업무 층의 깊이 있는 사선 내부와 옆쪽 층 안내·공간 목록으로 구성한다. 층 전체의 비율, 가구 군집, 유리 회의실, 엘리베이터와 연결 통로를 함께 설계한다. 전체 층 보기는 별도 탐색으로 제공하며 층 선택·업무 공간·직원 목록·대화 연결은 실제로 작동해야 한다.
- Commander는 복도를 거쳐 방에 입장하고 퇴실할 수 있어야 한다. 현재 위치와 이동 경로를 표시하고, 방 선택·키보드 조작·작은 화면에서도 같은 업무 흐름을 제공한다. 자유 이동형 3D는 별도 결정이지만 복도 이동과 방 입장은 필수다.
- 업무 지시·질의응답·업무보고·결과 검토는 입장한 방의 작업 화면과 연결한다. 사무실은 직원 업무와 CLI 세션, 회의실은 직원·세션 간 협업, 대표이사실은 Commander에게 하는 질문·발표·보고·승인, 휴게실·다과실은 대기와 휴식 공간으로 구분한다. 공간 이동만으로 실제 CLI 실행을 시작·중지하거나 업무 상태를 바꾸지 않는다.
- 확인된 협업 이벤트는 참여한 직원·세션의 회의실 이동과 논의 동작으로, Commander 질문·승인 대기는 대표이사실 이동과 프레젠테이션 동작으로 표현한다. 복도·문·엘리베이터를 거치며, 답변·완료·중단·관찰 연결 끊김·유효기간 종료에 따라 동작을 해제한다. 자동 갱신이 사용자의 카메라·방 선택·작성 중인 답변을 빼앗지 않는다.
- 활동은 지원되는 구조화 이벤트와 실제 체험 업무 상태만으로 판정한다. 일반 대화 문장·추론·웹 탭 열림으로 협업이나 질문을 추정하지 않는다. 단발성 협업 전달은 시간 제한이 있는 최근 이벤트로 표시한다. 종류·시각·선택한 프로젝트의 참여 세션 ID만 연결기 로컬 상태파일과 서버 메모리에 두고, 질문·도구 원문과 활동 요약을 Git·이미지·검색 보관·인계에서 제외한다. 공급자의 질문 답변·실행 승인은 원래 지원 인터페이스에서 처리한다.
- CLI 목록·캐릭터·방 안의 세션을 클릭하면 대화 모달을 즉시 열어 하단까지 스크롤하는 부담을 없앤다. 공간 이동 완료를 기다리지 않으며 모달 안에서 세션 전환·검색·필터·최신 이동·지시 화면을 제공한다. 닫기·재열기·갱신 중 읽던 위치와 검색 조건을 보존하고 키보드·모바일 가독성 기준을 지킨다.
- CLI 대화기록은 선택한 세션의 사용자 지시와 공개된 에이전트 응답을 시간순으로 읽는 터미널 형태의 UI로 제공한다. 세션·역할·시각·연결 상태·기록 범위와 잘림 여부를 표시하고 검색, 역할 필터, 최신 기록 이동을 지원한다. 기록을 읽는 동안 새로고침이 스크롤과 입력을 빼앗지 않도록 한다.
- 대화 연동은 선택한 로컬 작업 공간으로 한정한다. 명시적으로 활성화한 연결 프로그램에서 제한된 최근 기록을 읽으며, 시스템 지침·내부 추론·도구 원문·인증 정보는 제외하고 알려진 비밀 정보와 개인 경로를 마스킹한다. 대화기록은 Git·이미지·공개 Wiki·인계 내보내기에 넣지 않는다. 연동 미설정·기록 없음·연결 끊김을 예시 대화나 성공 상태로 대신하지 않는다.
- 연결 관리의 설정에서 공개 대화 읽기·CLI 검색 보관·Codex 지시 전송을 별도로 선택하고 저장한다. 최초에는 모두 꺼 두고 수집 범위·보관 여부·권한을 각 선택 옆에 설명한다. 저장한 설정은 이 사무실의 호스트 연결 프로그램에 적용하며 다음 실행에도 유지한다. 기존 CLI 옵션은 저장된 화면 설정이 없을 때 사용하는 고급 호환 경로로 둔다.
- 설정 저장과 실제 적용을 구분한다. 최신 연결 프로그램은 실행 중 변경을 읽고 적용한 설정을 응답한다. 미연결·구버전·저장 실패·권한 부족·CLI 미지원에는 다음 조치를 표시하며 적용 확인 전 성공으로 표시하지 않는다. 설정을 끄면 새 수집·전송을 중지하되 이미 전송 중인 지시와 기존 검색 사본의 처리 범위를 안내한다.
- 대화 미설정·검색 미연결 화면에서 해당 설정으로 바로 이동할 수 있게 하고, 주 탐색에도 연결 설정 진입점을 둔다. 최초 호스트 실행이 필요한 경우 실행 장소·시점·유지해야 하는 터미널과 복사 가능한 기본 명령을 안내한다. 브라우저가 호스트 프로그램을 실행한 것처럼 표시하지 않으며 작성 중인 설정은 자동 갱신이 덮어쓰지 않는다.
- 사무실 이름·상태·버튼·탐색 항목의 불필요한 강제 줄바꿈과 좁은 폭 때문에 생기는 어색한 두 줄 표시를 없앤다. 긴 설명은 자연스럽게 줄바꿈하고 모바일에서도 읽기와 조작을 유지한다.
- 감지 목록과 연결 점검은 하나의 연결 관리 패널 안에서 탭으로 전환하고 선택한 내용만 표시한다. 탭 전환·자동 갱신 중 필터와 선택을 유지하며 키보드로도 전환할 수 있게 한다.
- 로컬 세션에는 공식 지원 경로로 실제 지시를 전달한다. 큐 접수와 업무 완료를 구분하고, 전송 여부가 불확실하거나 연결이 끊기면 같은 지시를 자동 재실행하지 않는다.
- 연동 준비 중인 공급자에도 공식 서비스 접속 링크와 Wiki 연결 안내를 제공한다. 외부 서비스 로그인과 사무실의 실제 에이전트 연동 상태는 구분한다.

- 기능과 실행 방법이 바뀌면 README도 함께 갱신하고, 소개는 간결하게 유지한다.

## 10. Git 변경 기록과 동기화

- 개발 중 의미 있는 작업 단위가 완료될 때마다 검증 후 커밋하고 연결된 원격 브랜치에 푸시하여 변경 히스토리를 남긴다. 전체 작업이 끝날 때까지 기록을 미루지 않는다.
- 커밋은 하나의 목적에 집중하고, 변경 의도를 알 수 있는 짧은 제목을 작성한다. 예: `docs: add user guide`, `feat: add agent registration`, `fix: restore interrupted tasks`.
- 커밋 전 변경 목록과 diff를 확인하고 관련 파일만 명시적으로 스테이징한다. 로컬 참고 자료와 민감 정보는 제외한다.
- 푸시 실패 시 로컬 커밋을 보존하고 원인을 보고한다. 강제 푸시나 기존 이력 덮어쓰기로 해결하지 않는다.
- PC 이동 전 푸시 결과를 확인하고, 다른 PC에서는 작업 전에 원격 변경을 가져와 충돌 여부를 확인한다.
- 이 정책은 개발 작업 기록에 적용한다. 제품이 사용자 작업을 자동 commit/push하는 기능은 별도로 설계한다.

## 11. 사용자 Wiki 관리

- 사용설명서 원본은 docs/wiki/에서 코드와 함께 버전 관리하고 README에서 연결한다.
- Wiki에는 현재 제공 기능, 준비 사항, 시작 방법, 주요 사용 흐름, 문제 해결과 관련 문서를 정리한다.
- 미구현 기능은 예정으로 표시하고 실제 검증 전에는 설치·실행 절차를 확정된 안내로 게시하지 않는다.
- 기능이나 사용 흐름 변경 시 관련 Wiki도 같은 작업 단위에서 갱신한다.
- 사용자 도움말은 GitHub Wiki에 게시한다. 사용자가 만든 Home과 OfficeGuide 페이지를 활용하고, 화면의 도움말과 README는 게시된 Wiki로 연결한다.
- docs/wiki/의 원본을 GitHub Wiki와 함께 갱신한다. 페이지 내용과 링크를 확인하고 게시 여부를 명확히 구분한다.

## 12. 버전과 Release 관리

- 릴리스 버전은 MAJOR.MINOR.PATCH(대.중.소), Git 태그는 vMAJOR.MINOR.PATCH 형식을 사용한다.
- 대(MAJOR): 기존 사용법·설정·데이터와 호환되지 않는 변경. 이전 방법과 주의 사항을 함께 기록한다.
- 중(MINOR): 기존 호환성을 유지하는 기능 추가. 소(PATCH): 호환성을 유지하는 오류 수정과 작은 개선.
- 초기 개발 버전은 0.x.y를 사용한다. 이 기간의 호환성 파괴 변경은 MINOR를 올리고 명시하며, 안정적인 사용 기준을 충족하면 1.0.0으로 전환한다.
- 변경은 CHANGELOG.md의 Unreleased에 추가·변경·수정·호환성 항목으로 누적한다. 모든 커밋마다 릴리스를 만들 필요는 없다.
- 릴리스 시 날짜와 버전을 확정하고 검증된 커밋에 태그를 연결한다. GitHub Release에는 변경 요약, 검증 결과, 설치·업데이트 방법, 알려진 제한을 기재한다.
- 실행 가능한 배포물과 검증이 준비되기 전에는 정식 릴리스를 게시하지 않는다. 절차와 템플릿은 docs/releases.md를 따른다.
