# 개발 협업 기록

## 현재 동시 작업 운영

여러 개발 세션의 작업 범위와 통합 순서는 관리 담당이 조율한다. 기능 요구사항은 최신 `rules/rules.md`와 `rules/requirements.md`를 따르며, 미확정 제품 정책을 개발 세션의 편의로 확정하지 않는다.

| 역할 | 책임 |
| --- | --- |
| 관리 담당 | 우선순위·파일 담당·의존 순서를 정하고, 변경과 검증 근거를 검토하여 통합한다. |
| 기능 담당 | 배정받은 파일과 변경 구간을 구현하고 관련 테스트·사용 안내·남은 문제를 인계한다. |
| 검증 담당 | 지정된 커밋 또는 고정된 변경 사본을 검증하고 재현 조건과 결과를 보고한다. 수정이 필요하면 먼저 담당을 정한다. |

- 같은 작업 폴더의 Git index와 실행 환경은 공유된다. commit/push와 Docker·Wiki 반영은 관리 담당 또는 관리 담당이 지정한 한 세션만 수행한다.
- 파일 전체 또는 명시한 변경 구간에 담당을 정한다. 공통 파일의 수정이 겹치면 순서를 나누거나 별도 작업 사본에서 패치를 인계한다. 다른 세션의 변경을 덮어쓰거나 일괄 스테이징하지 않는다.
- 진행 중인 변경이 섞여 있으면 먼저 보존하고 소유 범위를 확인한다. 혼합된 작업 트리의 테스트 통과만으로 개별 기능의 완료를 판단하지 않는다.
- 인계에는 목적, 기준 커밋, 변경 파일·공통 파일의 구간, 검증 명령·결과, 남은 작업, 사용자 결정이 필요한 사항을 포함한다.
- 기능 단위 검증과 변경 검토 후 목적별로 커밋·푸시한다. 함께 반영할 기능의 통합 검증이 끝나면 확정된 커밋으로 배포하고 실제 동작·상태를 확인한다.
- 구현 완료, 검증 완료, Git 반영, 실행 환경 반영을 구분해 보고한다. 새 사용자 지시나 작업 범위 변경은 관리 담당에게 전달한다.
- 세션 식별자·대화 원문·임시 작업판은 로컬에서만 관리하고 제품·공개 문서·커밋·배포물에 포함하지 않는다.

## 초기 구현의 담당과 작업 경계 — 과거 기록

아래는 초기 두 세션의 역할과 통합 기록이다. 현재 작업 배정과 통합 권한은 위 운영 기준을 따른다.

| 담당 | 소유 경로 | 현재 작업 |
| --- | --- | --- |
| 서버 세션 | server/, scripts/, tests/server/, package.json, package-lock.json, Dockerfile, compose.yaml, .dockerignore, .gitignore, .env.example | API·SQLite·Docker 및 Codex 관찰·지시 전달 구현·검증 |
| 웹 세션 | public/, tests/ui/, docs/wiki/UI.md | HTML/CSS/JS 사무실 GUI와 자체 제공 Three.js 입체 화면 구현 |
| 서버 세션 통합 | README.md, CHANGELOG.md, docs/wiki/Home.md, rules/ 문서, docs/api.md | 실행 검증 후 실제 구현 범위 반영 |

- 초기에는 서버 세션이 통합과 commit/push를 담당하고 웹 세션이 완료 파일 목록과 검증 결과를 전달했다.
- Docker 기본 주소는 http://localhost:8080 이다. 웹 개발 서버는 /api 요청을 http://localhost:8080 으로 프록시한다.
- 서버는 public/을 정적으로 제공한다. 웹 앱 빌드 단계는 없으며 Three.js 배포 파일과 라이선스를 저장소에서 자체 제공한다. 의존성 갱신 절차는 [개발 안내](development.md)를 따른다.
- 기존 Codex는 호스트 연결 프로그램의 명령 허용 모드에서 공식 큐로 지시한다. 신규 실제 AI 실행·다른 공급자 제어는 미구현이다. 데모는 별도 공급자 demo로 표시하고 실제 모델 추론으로 표현하지 않는다.
- API 계약은 [api.md](api.md)를 기준으로 한다. 화면은 응답에 없는 기능을 추정하지 않는다.

## 웹 진행 메모

- 구현 완료: public/의 사무실·직원·업무·인계 화면, 프로그램·블로그 배너, 레드 테마·자체 호스팅 폰트·상태 캐릭터·CLI 관찰 UI, tests/ui/ 15개 테스트와 docs/wiki/UI.md.
- 브라우저 검증: 직원 채용 → 업무 → 답변 → 승인, 중지·재개, JSON 다운로드, 외부 직원 등록과 실행 비활성화, 연결 끊김 안내, 390px 반응형 화면 확인.
- 웹 세션의 파일 수정과 별도 테스트 서버 운영을 마치고 서버 세션에 통합을 인계했다.

## 서버 진행 메모

- 구현 완료: SQLite 영속 저장, 직원 등록, 데모 업무·질문·승인, 사무실 일시 중지, 인계 내보내기, Docker 구성.
- 검증: 서버 19개 테스트 및 UI 포함 통합 34개 테스트 통과. 별도 Docker 검증 환경에서 정상 종료·재시작·승인 단계 복원, 비루트 실행과 이미지 포함 파일 확인.
- 최종 UI 파일과 문서 통합 완료. 기본 http://localhost:8080 에 Docker 컨테이너를 실행하고 서버 연결·사무실 재개·직원 채용 화면을 확인했다.
- 후속 구현: `OFFICE_NAME` 설정, StackQueue Blog 배너 데이터, 호스트 Codex 관찰 프로그램과 `localSessions` 상태 API. 실제 두 세션의 상태만 전달하며 새 Docker 화면에서 표시됨을 확인.
- 후속 구현: 공식 Codex 큐 지시, 요청 ID 중복 방지와 접수 조회, 전달 전 원문 제거, 연결 프로그램 재시작·시간 초과 시 자동 재실행 방지. 서버 26개 테스트 통과와 실제 API→호스트→Codex 큐 접수 확인.
- 최종 통합: 회사 구역 배치와 CSS 정리, 기존 세션 지시·접수 화면, 세션 순서 고정. 320·390·768·1366px 검증, 서버 26개+UI 22개 총 48개 테스트 통과. 기본 Docker에서 한글 지시의 공식 큐 접수 확인.
- 후속 범위: 신규 실제 AI 세션 실행, 다른 공급자 업무 실행, 실제 CLI 승인·중단과 모델 변경.
- 후속 통합: 공급자 공식 접속 링크·Wiki 준비 안내, 공급자 링크 고정 허용 목록. 전체 49개 테스트 통과, 기본 Docker와 320px 모바일 배치 확인.
